# dedupe-docs —— 言い換えによる重複を意味で見つけて解消する

verify-docs の重複検査は「段落がそのまま一致するか」しか見ない。**コピペ
した重複は防げるが、同じ内容を自分の言葉で書き直した重複は素通りする。**
本スキルはこの隙間を、チェッカーではなく人・エージェントの判断で埋める。

## 前提

対象リポジトリに verify-docs 一式（`scripts/verify-docs.mjs` と
`.claude/skills/verify-docs/`）が導入済みであること。本スキルは
verify-docs の検査対象・設定・規約（`allow-duplicate` マーカーなど）を
そのまま流用する。verify-docs 自体の規約は
[verify-docs/SKILL.md](../verify-docs/SKILL.md) を参照する（本ファイルでは
重複させない）。

## 手順

### 1. 機械的な重複を先に片付ける

```bash
node scripts/verify-docs.mjs
```

`[重複]`・`[準一致重複]` が出力された場合は、まずそちらを
[verify-docs/SKILL.md](../verify-docs/SKILL.md) の「3. 重複を特定する」の
手順で解消する。**意味的な重複の判定は、機械的な重複が無い状態を前提に
行う**（機械的な重複が残ったままだと、どちらが本来の重複源か判断しづらい）。

### 2. 文書群を通読し、意味的な重複を探す

対象は verify-docs が検査する文書一式と同じ（`excludePaths` で除外した
ディレクトリを除くリポジトリ全体の `*.md`。詳細は
[references/config.md](../verify-docs/references/config.md) の
「検査対象の集め方」を参照）。**文字列としては一致しなくても、同じ主張・
同じ手順・同じ判断基準を説明している段落が複数の文書に無いかを判断する。**

**作業開始時に、対象文書の一覧を単一のチェックリストとして作る。** 出力先は
実行環境のタスク管理機能（Claude Code の `TaskCreate`/`TaskUpdate` など）が
使える場合はそれを使う。使えない場合は、リポジトリ直下の
`.verify-docs/dist/` 配下に日時・作業内容が分かるファイル名
（例: `2026-09-12-todo-dedupe.md`）で、チェックボックス形式
（`- [ ] 文書パス`）で書き出す。**手段を問わず、置き場所は1つに保つ**
（会話中の複数メッセージに分けて書く、同じ作業のリストを複数ファイルに
分散させる、といったことはしない）。`.verify-docs/` は
[config.md「作業チェックリストの保管先」](../verify-docs/references/config.md#作業チェックリストの保管先verify-docs)
の通り検査対象から除外されるため、**作業ログとして削除せず残してよい**。

**リストの並び順は、確認する順番をそのまま表す。** 項目の並び替え・削除は
行わない——確認済みの項目もチェックを付けたまま残し、消さない。これにより
リストを見るだけで「何を・どの順で確認する予定か」と「どこまで終わったか」
の両方が常に分かる状態を保つ。

文書を1件確認し終えるたびに、その項目にチェックを入れ、**日時・担当・
判断理由を書き添える**（`verify-docs.todo.json` の `reason` 欄・
`allow-duplicate` マーカーの理由コメントと同じ考え方）。実行環境のタスク
管理機能を使う場合は日時・担当（セッション ID など）は機能側の記録に
任せてよいが、判断理由（例:「重複なし」「X に統合しポインタ化」「要人確認」）
は項目ごとに明記する。

単一のメッセージ・単一のファイルで管理する場合の例（3件中2件を確認済み、
1件は未確認のまま次に控えている状態）:

```markdown
- [x] README.md — 2026-09-12 / session_xxxx / 重複なし
- [x] CONTRIBUTING.md — 2026-09-12 / session_xxxx / SKILL.md と重複 → ポインタ化して統合
- [ ] verify-docs/README.md
```

**本手順の判定は再現性を
持たない（同じ入力でも見落としが起こりうる）と「3. 確信度で対応を分ける」
で明記している通りであり、その見落としの一種である「読んだつもりで読み
飛ばした文書」を機械的に防ぐのがチェックリストの役目である。** 全項目に
チェックが入るまで「3. 確信度で対応を分ける」には進まない。

よくあるパターン:

- 入口文書（README・CLAUDE.md など）の一文を、詳細文書（docs・SKILL.md
  など）が言い換えて再度説明している
- 詳細文書へのポインタを置いた直後に、そのポインタ先の内容を要約して
  重ねて書いている（「詳細は X を参照」と言いながら X の内容を先に
  書いてしまっている）
- 複数の詳細文書が、同じ前提・同じ手順を独立に説明している

### 3. 確信度で対応を分ける

- **確信できる場合**（同じ主張を別の言葉で書いているだけと明確に判断できる）
  → 完全一致の重複と同じ手順で是正する。本来の置き場所（より詳細・より
  下位の文書）を決め、他方はポインタ1行に置換する。**「移動とポインタ化」
  のみとし、要約・言い換えによる内容変更は行わない**
  （[verify-docs/SKILL.md「守ること」](../verify-docs/SKILL.md#守ること)
  を参照）
- **確信が持てない場合**（意味が重なるのは一部だけ、対象読者・文脈が
  異なる、片方が抽象度の高い要約でもう片方が手順の詳細、など）→
  **その場で断定して統合しない。** 検出内容と根拠を人に報告し、統合するか
  意図した重複として残すかの判断を仰ぐ
- **意図して重複させるべき場合**（免責文言・定型の注意書きなど）→
  [config.md「意図した重複を許可する」](../verify-docs/references/config.md#意図した重複を許可する)
  の `allow-duplicate` マーカーを使う。本スキルによる統合の対象からも外す

**本手順の判定はチェッカーと異なり再現性を持たない**（同じ入力でも
見落とし・過検知が起こりうる）。誤った統合を単独で確定させないこと。

### 4. 是正後に再検査する

```bash
node scripts/verify-docs.mjs
```

ポインタ化に伴うリンク切れ・断片リンク切れ・サイズ超過が発生していないか
機械的に確認する。**本スキルの是正がverify-docsの検査を新たに壊していないか
を、この一手で担保する。**

## 完了条件

以下を全て満たした時点で完了とする。

- チェックリストの全項目にチェックが入っている（未確認のまま残っている
  文書が無い）
- 確信できた重複は是正済み、確信が持てなかったものは検出内容・根拠と
  ともに人へ報告済みである
- 「4. 是正後に再検査する」の `node scripts/verify-docs.mjs` が
  「文書構造: すべて通過」で終わっている

## 対象外とする範囲

- **重複の判定を自動化・機械化すること。** LLM 判定は再現性を持たないため、
  CI の pass/fail には使わない（verify-docs のチェッカーには組み込まない）
- **文章の品質・正確性の判断。** verify-docs 本体と同じく、判定するのは
  「同じ内容が重複しているか」のみであり、内容の正否・簡潔さは対象外
- **意味的な類似度のしきい値の数値化。** 「何%似ていたら重複とみなすか」
  のような機械的な基準は設けない。判断そのものを人・エージェントに委ねる
