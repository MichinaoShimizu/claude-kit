# 設定ファイルの中身

`.claude/skills/verify-docs/SKILL.md` から参照される。検査スクリプトの設定を
変更する場合・TODO ファイルの記述形式を確認する場合・意図した重複の許可方法を
確認する場合に参照する。

## `verify-docs.config.json`

リポジトリ直下に配置する。存在しない場合は全項目が既定値で動作する。
**設定項目名と意味は、下表を正本とする。** README.md・CONTRIBUTING.md
など他の文書では個々のキー名を列挙せず、本表を指すだけにとどめる
（キーを追加した際に一覧が複数箇所に分散し、一部の更新漏れに気づけなく
なることを防ぐ。追加時は本表への追記が漏れていないか
`verify-docs.test.mjs` が機械的に検査する）。

```json
{
  "entryPoints": ["README.md", "CLAUDE.md", "AGENTS.md"],
  "docsDir": "docs",
  "skillsDir": ".claude/skills",
  "pathRoots": ["src/", "docs/", "scripts/", ".claude/", ".github/"],
  "excludePaths": ["node_modules/", ".git/", "vendor/", "dist/", "build/", ".verify-docs/"],
  "maxDocBytes": 30000,
  "minDuplicateChars": 60,
  "checkDuplicates": true,
  "checkNearDuplicates": false,
  "todoFile": "verify-docs.todo.json"
}
```

| キー                  | 意味                                                                 |
| --------------------- | ---------------------------------------------------------------------- |
| `entryPoints`         | 索引となる文書。他から参照されていなくてよい起点（CLAUDE.md・AGENTS.md はルーティングテーブルに徹する。下記「入口の既定値」を参照） |
| `docsDir`             | 話題ごとの詳細文書を配置するディレクトリ                             |
| `skillsDir`           | スキル定義を配置するディレクトリ（`<skillsDir>/<name>/SKILL.md` を想定） |
| `pathRoots`           | 本文中のバッククォート表記をパスとして検査する接頭辞                 |
| `excludePaths`        | 検査対象から除外するディレクトリ（下記「検査対象の集め方」を参照）。既定に含まれる `.verify-docs/` は dedupe-docs スキルのチェックリスト保管先（下記「作業チェックリストの保管先」を参照） |
| `maxDocBytes`         | 1文書あたりの上限（バイト数）。超過時は分割するか TODO に記載する    |
| `minDuplicateChars`   | 重複検査の対象とする段落の最小文字数。値が小さいほど誤検知が増加する |
| `checkDuplicates`     | 完全一致の重複検査の有効・無効。既定は有効                           |
| `checkNearDuplicates` | 準一致の重複検査の有効・無効。既定は無効（下記「準一致重複」を参照） |
| `todoFile`            | 例外リストの配置先                                                   |

### 検査対象の集め方

**`entryPoints`・`docsDir`・`skillsDir` に置かれた文書だけを見る方式は
採らない。** 特定の場所だけを見る方式（許可リスト）だと、そこに置き忘れた
文書が検査から漏れたまま気づかれない（例: リポジトリ直下に新しく作った
`CONTRIBUTING.md` が `entryPoints` にも `docsDir` にも無く、孤立チェック・
重複チェックのどちらにも一切かからなかった事故）。

そのため、`excludePaths` に列挙したディレクトリ（既定は `node_modules/`・
`.git/`・`vendor/`・`dist/`・`build/`）を除き、**リポジトリ全体の `*.md` を
検査対象とする（許可リストではなく除外リスト）。** `entryPoints`・
`docsDir`・`skillsDir` は「検査対象に入れるかどうか」ではなく、「その文書に
何を期待するか」（孤立チェックを免除する起点か、`SKILL.md` の目次に載る
べき補助文書か）を決めるためだけに使う。

モノレポで各パッケージを個別に `--root=packages/<name>` で検査する場合
（「Python プロジェクト・モノレポでの導入」を参照）は、リポジトリ直下の
検査からパッケージのディレクトリを二重に検査しないよう `excludePaths` で
除外する。

`maxDocBytes` の設定方針: 初期段階から厳格な値にしないこと。まず上限なしで
検査を実行し、現存する文書のうち最大サイズで「このままで問題ない」と
判断できるものより1〜2割大きい値を初期値とする。過度に厳格にすると、
正当な理由がある文書まで分割を強制することになる。

`minDuplicateChars` の設定方針: 既定値の60は「短い定型句レベルの一致では
検出しない」ための下限である。誤検知（意味のない一致で検出される）が
多い場合は値を上げ、見逃し（実際の重複を検出できない）が多い場合は
値を下げる。`checkNearDuplicates` を有効化した場合も同一の値が適用される。

### 準一致重複（`checkNearDuplicates`）

完全一致の重複検査では、句読点や敬体/常体（です・ます調 / だ・である調）の
違いのみを持つ段落を検出できない。`checkNearDuplicates` を `true` に
設定すると、句読点の全角/半角、および代表的な敬体語尾（「です」「ます」
「ございます」など）を正規化した上で再比較する。**意味的な類似判定では
なく、定型文字列の置換のみによる機械的処理である。** 完全一致で既に
検出済みの組は二重に報告しない。

既定で無効としているのは、完全一致より判定基準を緩めると誤検知が
増加するためである。有効化して誤検知が多い場合は `minDuplicateChars` を
上げるか、意図した表記差には `<!-- verify-docs:allow-duplicate -->` を
使用する（「意図した重複を許可する」を参照）。

### 入口の既定値

`entryPoints` の既定値には `CLAUDE.md` と `AGENTS.md` の両方を含める。
いずれもエージェント向けの入口ファイルという同一の役割を持ち、使用する
CLI・エージェントによって名称が異なるのみである。**両方が存在するリポジトリ
でも、片方のみのリポジトリでも、既定値のまま動作する**（存在しない側は
`entryPoints.filter(existsSync)` により自然に除外される）。

この2つに共通する原則の詳細は [SKILL.md](../SKILL.md) の
「1. 入口を軽量化する」を参照する。本検査はサイズと重複のみを検査するため、
**「ルーティングテーブルに徹しているか」自体は機械では判定できない。**
入口が肥大化している、道案内であるべき箇所に理由の説明まで記載されている、
といった兆候は人が検出する。

### Python プロジェクト・モノレポでの導入

**`docsDir`・`skillsDir`・`pathRoots` はいずれも上書き前提の項目であり、
JavaScript/TypeScript 以外の構成でも既定値の考え方は変わらない。** 対象
リポジトリの慣用ディレクトリ名に合わせて `pathRoots` を書き換える。

Python プロジェクト（`tests/` を使う構成）の例:

```json
{
  "pathRoots": ["src/", "tests/", "docs/", "scripts/", ".claude/", ".github/"]
}
```

**モノレポ（`packages/<name>/` 配下に各パッケージが独立した文書一式を
持つ構成）の場合は、リポジトリ直下ではなく各パッケージ内で
`--root=packages/<name>` を指定して実行する。** 1回の実行は1つの
`docsDir`・`skillsDir` の組しか検査しないため、パッケージ横断で検査
したい場合は `--root` をパッケージごとに切り替えて複数回実行する
（CI では、対象パッケージの数だけステップまたはジョブを分ける）。

## `verify-docs.todo.json`

**上限を超過しているが、現時点では分割できない文書の申告リスト。** 超過を
検査から除外するのではなく、超過を認めた上で「認識した上で残している」旨を
毎回の実行結果に出力し続けるための仕組みである。手動記述も可能だが、
既存リポジトリへの初回導入時は `node scripts/verify-docs.mjs --init-todo`
により、その時点の違反を一括で書き出せる。

```json
[
  { "path": "docs/deploy.md", "reason": "初期設定と独自ドメインの節がまだ混ざっている" }
]
```

- **`path` はリポジトリ直下からの相対パスとする。** 検査対象の文書一覧に
  存在しないパスを記載すると「この文書は既に存在しない」で検査が失敗する
  （削除漏れの検知機構）
- **`reason` は必須ではないが記載を推奨する。** 後で参照する者（将来の
  自分を含む）が「なぜ残存しているか」を追跡できるようにする
- **是正後は削除すること。** 上限内に収まった文書がなお記載されていると、
  「既に上限内に収まっている」で検査が失敗する

新規導入リポジトリで、既存文書がまとめて上限を超過している場合は、
`--init-todo` によりその時点の全件を書き出してから運用を開始してよい。
以降は新規文書・追記文書から上限を遵守し、TODO リストは削減する方向に
のみ運用する。

## 意図した重複を許可する

免責文言・定型の注意書きなど、**意図的に**複数文書へ同一段落を配置したい
場合がある。該当段落の直前行に、単独行として以下を配置する。

```markdown
<!-- verify-docs:allow-duplicate -->
この段落はこども向けページと大人向けページの両方に意図して重複させている。
```

マーカー直後の1段落のみが重複検査から除外される。**サイズ超過の TODO と
異なり、ファイルには痕跡が残らない。** 段落そのものの近傍に理由を記載
できるため、コメントとして「なぜ重複させているか」も併記することを推奨する。

## 作業チェックリストの保管先（`.verify-docs/`）

[dedupe-docs スキル](../../dedupe-docs/SKILL.md)・本 SKILL.md の検査手順が
作るチェックリストは、実行環境のタスク管理機能が使えない場合、リポジトリ
直下の `.verify-docs/dist/` 配下に保管する。**`excludePaths` の
既定値に `.verify-docs/` を含めているのはこのため**であり、チェックリストは
検査対象（参照整合性・サイズ・重複）から常に除外される。作業ログとして
削除せず残してよい（履歴として蓄積する）。ファイル名は日時・作業内容が
分かる形式（例: `2026-09-12-todo-dedupe.md`）とし、1回の作業につき1ファイルに
まとめる（同一作業のチェックリストを複数ファイルに分散させない）。
