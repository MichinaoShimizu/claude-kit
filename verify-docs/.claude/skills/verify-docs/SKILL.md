# verify-docs —— 必要な時にだけ必要な文書を読ませる

生成AIエージェントは、セッションの最初に CLAUDE.md・AGENTS.md・README を読み、
作業の途中で関連する docs や `.claude/skills/*/SKILL.md` を読みに行く。
**この「読みに行く」の設計が壊れると、関係ない決め事まで毎回トークンを食う。**

壊れ方は3つ。

1. **入口が太る。** CLAUDE.md・AGENTS.md・README に「その場では要らない
   詳細」まで書いてあると、セッションを開くたびにそれを読むことになる
2. **個々の文書が太る。** 「この話題のときに開く」という区切りがあっても、
   その1文書の中身が際限なく増えると、開いた瞬間の読む量が膨らむ
3. **同じ説明が複数の文書に重複する。** コピーしてから直すと、片方だけ
   更新されて矛盾した2つの説明が残る。文書を分割するときにも起きやすい

## 守ること

**分割・重複解消は「移動」と「ポインタ化」だけで行う。要約・言い換え・
簡略化で内容を変えない。** このスキルが直すのは構造（どこに書いてあるか）
であって、内容（何が書いてあるか）ではない。特に数値・条件・手順の順序・
免責文言は一字一句動かさない。「ついでに読みやすく整える」を混ぜると、
意味が変わったことに誰も気づけないまま分割だけが完了した状態になる。

内容そのものを見直したい（古い・冗長・分かりにくい）なら、それは
このスキルの仕事ではなく、別の作業（内容のレビュー・書き直し）として
分けて行う。1つの変更に「構造を直す」と「内容を直す」を混ぜると、
どちらの変更で意味が変わったのかを追えなくなる。

## チェッカーとプレイブックを分ける

このスキル一式は2つに分かれている。**同じ回で両方を兼務させない**
（審査するものと審査されるものが同じ判断基準を持つと、審査が甘くなる）。

- **チェッカー**（`scripts/verify-docs.mjs`）—— 機械的に判定できることだけを見る。
  参照切れ・孤立・サイズ超過・完全一致の重複。**「これは MUST に値するか」
  「文章として自然か」のような判断はしない**
- **プレイブック**（このファイル）—— チェッカーが見つけたものを、人やエージェントが
  どう直すかの手順。判断が要るところはここに書く

## 使う前に

`scripts/verify-docs.mjs` をこのリポジトリに置く（このスキル一式をまるごと
コピーしてくれば入っている）。設定は `verify-docs.config.json`
（無ければ既定値。[references/config.md](references/config.md)）。

```bash
node scripts/verify-docs.mjs
```

これは**壊れていることを教えてくれるだけ**で、直すのはこのスキルの仕事。

## 手順

### 1. 入口を軽くする

CLAUDE.md・AGENTS.md（または README）を開いて、**「常に効いている決め事
（MUST）」と「道案内（どの話題のときにどの文書を開くか）」だけ**が
残っているか確かめる。**この2つの入口ファイルはルーティングテーブルに
徹する** —— 話題と行き先の対応表であって、理由や手順を書く場所ではない。

それ以外 —— 理由・手順の詳細・過去の事例 —— が本文に書いてあったら、
docs ディレクトリ（設定の `docsDir`）に切り出して、入口には1行のポインタ
（表の1行でよい）だけ残す。**判断基準は「この段落を読まなくても、
次に何をすべきかは分かるか」。** 分かるなら詳細は外に出してよい。

この判断は機械にはできない。**「タイトに削れるか」も同じで、冗長な言い回しを
削って詰められるかどうかは、書いた本人か原則審査の役目。** チェッカーが見ているのは
サイズという結果だけで、削り方そのものは検査しない。

### 2. 太った文書を見つける

```bash
node scripts/verify-docs.mjs
```

`[サイズ超過]` が出た文書が対象。**まず中身を見出しで分ける。** よくある切り方:

- **手順の中に「一度きり」と「毎回」が混ざっている** → 一度きりの初期設定を
  別文書に出す（例: `deploy.md` から `deploy-setup.md` を切り出す）
- **1つの見出しの下に複数の独立した話題が並んでいる** → 見出し単位でファイルを分け、
  元の文書からは1〜2行のポインタで指す
- **過去の作業記録・棚卸しの結果が本文に混ざっている** → 別文書（`review-YYYY-MM.md`
  のような一過性の記録用）に出す

分けたら、**元の文書に残った内部リンク（`#見出し`）が、移動した先を指していないか**
必ず確認する。移動先の断片リンクは `他ファイル.md#見出し` の形に直す。
**分割は重複を生みやすい作業でもある。** 同じ段落をコピーして両方に残していないか、
分けたあとにもう一度検査を通す（次の「3.」）。

### 3. 重複を見つける

`[重複]` が出たら、同じ内容が複数の文書にそのまま存在している。

- **どちらが本来の置き場所かを決める。** 話題として詳しいほう・より上位の
  文書（README よりは docs）に残し、もう片方はポインタ1行に置き換える
- **どちらも独立に存在すべき理由があるなら**（例: 免責文言をこども向けと
  大人向けの両方に出す必要がある）、重複させたい段落の直前に
  `<!-- verify-docs:allow-duplicate -->` を置いて検査から外す。
  **これは「見なかったことにする」のではなく「意図した重複だと宣言する」**
  ための印なので、乱用しない

### 4. まだ分割できないなら、TODO に書く

既存の大きいリポジトリに後から入れると、その場で全部は分割できない文書が出る。
**黙って超過させたまま放置しない。** `verify-docs.todo.json`
（既定のファイル名。[references/config.md](references/config.md)）に
理由つきで書く。

```json
[
  { "path": "docs/deploy.md", "reason": "初期設定と独自ドメインの節がまだ混ざっている" }
]
```

これで検査は落ちなくなるが、**`node scripts/verify-docs.mjs` を走らせるたびに
一覧に出る。** 見なかったことにできない状態を作るのが狙い。
直したら **エントリを消すこと。** 消し忘れると `[TODO の掃除]` で検査が落ちる
（直したのに借金が残ったふりをしている状態を許さない）。

### 5. CI に差し込む

push・PR の前に必ず通るようにする。差し込み方は [README.md](../../../README.md) の
「CI に足す」を見る。**ローカルで手元に置くだけでは、直後にまた太る。**

### 6. 維持する

一度直しても、書き足すたびにまた太る・また重複する。**新しい文書を足す回・
既存の文書に書き足す回のたびに `node scripts/verify-docs.mjs` を通す**のを
push 前検証の一部に入れておけば、崩れた瞬間に機械が教えてくれる。

## 対象にしないこと

- **文章の質や正確さは見ない。** 見ているのは構造（参照・孤立・サイズ・重複）だけ
- **何を書くべきかは判断しない。** 「この決め事は MUST か、道案内で十分か」
  「どちらの表現がタイトか」の判断は人か、そのリポジトリの原則に照らして行う
