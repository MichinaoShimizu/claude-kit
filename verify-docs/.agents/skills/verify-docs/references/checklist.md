# 作業チェックリストの作り方

[verify-docs スキル](../SKILL.md)・[dedupe-docs スキル](../../dedupe-docs/SKILL.md)
の両方から参照される。verify-docs 側に置くのは、dedupe-docs が任意導入
（[verify-docs/README.md「導入」](../../../../README.md#導入)）なのに対し
verify-docs 自体は検査実行前に必ずこの手順を要求するため（依存の向きを
逆にしない）。意味的重複の探索・機械チェックの是正のいずれを始める前にも、
本ファイルの手順でチェックリストを先に作る。

## 物理ファイル作成（必須）

作業開始時に、対象文書の一覧（または違反一覧）をチェックリストとして
リポジトリ直下の `.verify-docs/dist/checklist.md` に物理ファイルで作る。
省略してはならない（タスク管理機能は記録が作業者の裁量に依存し省略や
消失に気づけないため正本にしない）。ファイル名は常に `checklist.md` に
固定する（日時サフィックス付きのファイルを毎回作ると増え続けるため）。
`excludePaths` の既定値に `.verify-docs/` を含めているのはこのためで、
チェックリスト自体は検査対象（参照整合性・サイズ・重複）から常に除外
される。

ファイルは1つだが中身は `## verify-docs` ・`## dedupe-docs` ・
`## tighten-docs` ・`## 完了レコード` の4セクション固定とし、この3スキルで共有する。
各スキルは自分のセクションだけを書き換え、単独実行時に `## 完了レコード` には手を
加えない（3スキルを続けて実行した場合の統合記録を1ファイルに残すため）。

ファイルが存在しない場合は、4セクションを空の状態で作成する。

```bash
mkdir -p .verify-docs/dist
cat > .verify-docs/dist/checklist.md <<'EOF'
# verify-docs-checklist

## verify-docs

（未実施）

## dedupe-docs

（未実施）

## tighten-docs

（未実施）

## 完了レコード

（未作成）
EOF
```

続けて、実行するスキルの見出しから次の `## ` 見出し直前までを丸ごと
書き換える（見出し行自体はスキル名のみ残し、実行時刻はその直下に記載する）。

```markdown
## verify-docs — 2026-09-12T23:45:02+0900

- [ ] 文書パス1
- [ ] 文書パス2
```

日時は `TZ='Asia/Tokyo' date +%Y-%m-%dT%H:%M:%S%z` で取得し、実行環境の
設定に依存せず JST で記録する（開始時刻の記録を兼ねる）。「まず自分の
セクションを空にしてから書く」ことで、前回と今回の記録が同一セクション内で
混在しないようにする。

チェックボックスの中身は実際の対象に置き換える。サイズ超過・重複・リンク切れを
`--json` で得た場合は、ファイル名だけでなく見出し階層と開始行も含める
（例: `docs/deploy.md > デプロイ > 独自ドメイン（42行目）`）。ASTの位置情報で
修正箇所を特定できるときは、文書全体を1項目にしない。実行環境のタスク管理
機能（`TaskCreate`/`TaskUpdate` など）は進捗の可視化に併用してもよいが
物理ファイルの代わりにはできない。置き場所は1つに保つ（複数メッセージに
分けて書く、別名のファイルを追加で作る、といったことはしない）。各
セクションが保持するのは、そのスキルを最後に実行した回の記録のみである
（現在進行中の作業の記録であり、過去の履歴を蓄積する場所ではない）。

## 実行結果と完了レコード

各スキルが単独で完了したときは、自分のセクション末尾に `### 実行結果` を記録する。
これは対象・実施内容・最終検査・判断保留だけを残す短い記録であり、リポジトリ全体の
集計やTODOを重複して書かない。

ユーザーが verify-docs・dedupe-docs・tighten-docs の連続実行を依頼し、3つすべてが
同じ回に完了したときだけ、最後に `## 完了レコード` を更新する。完了レコードは3つの
実行結果を統合した唯一の全体サマリーである。途中で止まった場合や単独実行では
`（未作成）` のままにする。各様式は [checklist-summary.md](checklist-summary.md) を参照する。

## リストの運用

リストの並び順は確認する順番をそのまま表す。項目の並び替え・削除は
行わない——確認済みの項目もチェックを付けたまま残す。これによりリストを
見るだけで「何を・どの順で確認する予定か」と「どこまで終わったか」が
常に分かる。

1件確認し終えるたびに、その項目にチェックを入れ（`- [ ]` → `- [x]`）、
日付・判断理由を書き添える（`verify-docs.todo.json` の `reason` 欄・
`allow-duplicate` マーカーの理由コメントと同じ考え方）。タスク管理機能を
併用する場合も、判断理由（例:「重複なし」「X に統合しポインタ化」「要人
確認」）は物理ファイル側に明記する。

記入例（3件中2件を確認済み、1件は未確認のまま次に控えている状態）:

```markdown
- [x] README.md > 導入（12行目） — 2026-09-12 / 重複なし
- [x] CONTRIBUTING.md — 2026-09-12 / SKILL.md と重複 → ポインタ化して統合
- [ ] verify-docs/README.md
```

この手順の判定は再現性を持たない（同じ入力でも見落としが起こりうる）。
「確認したつもりで確認し忘れた項目」・「チェックリストを作らずに検査だけ
実行してしまう」の両方を機械的に防ぐのがチェックリストの役目である。
全項目にチェックが入るまで次の判断段階には進まない。

### サイズ変更時の記録

分割・統合・ポインタ化によって文書のバイト数を変えた項目は、圧縮前
サイズ・圧縮後サイズ・圧縮率を該当項目に記載する。圧縮率は
`(1 - 圧縮後 / 圧縮前) * 100` で計算し、小数第1位までとする。

```markdown
- [x] verify-docs/SKILL.md — 2026-09-12 / チェックリスト作成手順を
      references/checklist.md へ切り出し / 11,549B → 11,269B（2.4%減）
```

## 完了時の記録

各スキルの完了時は自分のセクションに `### 実行結果` を記載する。3スキルを連続実行
した回だけ、すべての実行結果を踏まえて `## 完了レコード` を更新する。記載項目・
テーブル様式・記入例は [checklist-summary.md](checklist-summary.md) を参照する。
